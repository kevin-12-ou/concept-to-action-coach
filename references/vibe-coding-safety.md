# Vibe Coding 场景检查

仅在问题涉及 Codex、编程 Agent、AI 修改项目、部署或相关自动化时使用。先判断哪些风险与当前问题真正相关，再选择性说明。

## 任务范围

帮助用户区分：

- 本次必须完成的可观察结果；
- 未来想法和明确不在范围内的内容；
- 可能受影响的文件、模块、数据和外部服务；
- 什么条件算完成。

开始改动前通常应让 AI 了解项目目录、README、依赖配置、技术栈、相关代码、测试与构建命令以及环境变量说明。小型、局部、上下文已经明确的改动不必套用完整盘点流程。

## 揭示隐藏任务

把表面交付与完整功能分开。例如：

- “有登录页面”不等于安全认证、会话管理和用户数据隔离已经完成；
- “页面能显示”不等于交互、错误态和可访问性正确；
- “构建通过”不等于业务逻辑正确；
- “测试通过”不等于真实用户流程、权限与边界条件都安全。

根据功能检查容易遗漏的责任：数据存储、身份识别、授权、数据隔离、输入验证、错误处理、恢复策略、密钥管理，以及本地与部署环境的差异。只提与任务有关的项目。

## 权限和人工确认

以下动作通常需要缩小权限、预览变更或在执行前由用户明确确认：

- 删除或不可逆覆盖文件与数据；
- 数据库 schema 或生产数据变更；
- 认证、授权和访问控制变更；
- 支付、生产部署与付费资源；
- 密钥、环境变量、隐私数据；
- 第三方服务调用、发送邮件或对外发布。

说明具体风险和确认点，不要只给泛泛的“注意安全”。读取密钥的值通常没有必要；优先确认变量名、配置位置和是否存在。

## 验收和回退

把验证分成几个互补层面：

- 自动检查：静态检查、单元或集成测试、构建；
- 行为验证：目标用户是否能完成关键路径；
- 回归检查：哪些旧功能不能被破坏；
- 变更审阅：检查 diff 是否只包含预期改动；
- 风险验证：权限、边界条件、错误态和环境差异。

回退方式应与风险匹配。通常先保留稳定 Git 提交或备份，再做一个小改动、审阅 diff、运行验证并手动验收。不要建议覆盖用户尚未提交的工作，也不要把 Git 提交描述成唯一备份。

## 升级信号

从简单方法逐步升级：

- 一次性、明确任务：直接对话和工具调用通常足够；
- 方法需要反复复用且希望结果稳定：考虑 Skill；
- 步骤和分支大多固定：考虑 Workflow；
- 下一步取决于中间结果，且需要持续判断完成：考虑 Agent；
- 工作能被拆成真正独立且值得并行或专业隔离的职责：再考虑多 Agent。

多 Agent 会增加协调、上下文同步、冲突处理、成本和可观测性负担。仅在这些代价小于并行或专业分工收益时使用。
